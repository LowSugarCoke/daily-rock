第 2 課 / 先知道正確行為

切換情境，看 API 應該回什麼

這是預期行為模擬器，沒有呼叫正在開發的後端。

400 Bad Request

分類：BadRequest

"Rating must be between 1 and 5"

請修改輸入內容，再重試。

產品規則

  1. 輸入不合法：回 400，保留原本說明。
  2. 找不到資料：回 404，保留原本說明。
  3. 資料庫失敗：回 500，只顯示固定訊息 Something went wrong. Please try again.
  4. 三種 body 都是 JSON 字串，不是物件或未編碼的純文字。
  5. AppError 內仍保存完整的原始資料庫錯誤；回應手機時才改用固定訊息。

本題統一 handler 主動產生的應用錯誤。格式錯誤的 JSON 等 Axum extractor 拒絕不在本次範圍。

第 3 課 / 讀懂函式，不看實作

兩段轉換，各有一個責任

三種錯誤分類與函式外框已提供，讓這次 30 分鐘集中練習 trait。這是第 4 題的第一小段。

impl From<worker::Error> for AppError
fn from(error: worker::Error) -> Self

impl IntoResponse for AppError
fn into_response(self) -> Response
片段意思C++ 對照概念
enum AppError一個值，三種分類，每種可攜帶資料。攜帶資料的 std::variant，不是單純 enum。
impl Trait for Type讓型別遵守指定行為契約。實作介面的概念，但不必繼承基底類別。
From<worker::Error>定義來源型別如何轉成 AppError。轉換建構式的概念。
error: worker::Error接收原始錯誤的所有權。接收可移動進新物件的值。
-> Self回傳目前型別，也就是 AppError。回傳 AppError 物件。
into_response(self)消耗 AppError，產生包含狀態碼、標頭和 body 的回應。消耗物件並產生 HttpResponse 的方法概念。
Result<T, AppError>成功是 T，失敗是 AppError。C++23 std::expected<T, E>。
?成功取出值；失敗轉換錯誤並提早回傳。檢查 expected，失敗就轉換錯誤並 return；不是 throw。
分清兩件事：錯誤物件內保存什麼，以及使用者收到什麼。兩者不必相同。

常見走錯的地方

  • 把所有錯誤都當成 500，就分不出使用者輸入錯誤。
  • 只回正確文字、忘記狀態碼，前端仍可能誤判。
  • 手動拼 JSON，引號或換行容易編碼錯誤。
  • 太早把原始錯誤換成公開訊息，就失去真正原因。
  • 把錯誤變成 panic，就無法按約定回傳。
